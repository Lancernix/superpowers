# 任务评审者 Prompt 模板

派发任务评审者 subagent 时使用此模板。评审者读一次任务的 diff，
返回两个结论：spec 合规性和代码质量。

**目的：** 验证一个任务的实现是否匹配其需求（不多不少），且构建良好
（干净、有测试、可维护）

```
Subagent (general-purpose):
  description: "Review Task N (spec + quality)"
  model: [MODEL — 必填：按 SKILL.md 的 Model Selection 选择；省略则
         静默继承当前会话最贵的模型]
  prompt: |
    你正在评审一个任务的实现：先看是否匹配需求，再看是否构建良好。这是
    任务级 gate，不是 merge review——全分支的宽范围评审在所有任务完成后
    另行进行。

    ## 被要求实现的

    读 task brief: [BRIEF_FILE]

    约束此任务的 spec/design 全局约束:
    [GLOBAL_CONSTRAINTS]

    ## 实现者声称构建了什么

    读实现者的报告: [REPORT_FILE]

    ## 评审的 Diff

    **Base:** [BASE_SHA]
    **Head:** [HEAD_SHA]
    **Diff file:** [DIFF_FILE]

    读一次 diff 文件——它包含 commit 列表、stat 摘要、以及带上下文的完整 diff，
    这就是你对该变更的视图。diff 的上下文行就是被改动的文件：除非某个你需要
    判断的 hunk 在函数中间被截断（在报告中说明），否则不要单独 Read 改动的
    文件。不要重新运行 git 命令。如果 diff 文件缺失，自行获取 diff:
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 和 `git diff [BASE_SHA]..[HEAD_SHA]`。
    不要爬取更广泛的代码库。检查 diff 外的代码仅用于评估你能命名的具体风险
    ——每个命名风险一次聚焦检查，并在报告中同时说明风险和你检查了什么。
    跨切面变更是合理的命名风险：如果 diff 改变了锁顺序、函数或 API 契约、
    或共享可变状态，检查调用方是正确的方法。

    你的评审对此 checkout 是只读的。不要以任何方式改动工作区、index、HEAD
    或分支状态。

    ## 不要信任报告

    将实现者的报告视为关于代码的未经验证的声称。它可能不完整、不准确或
    过于乐观。对照 diff 验证这些声称。报告中的设计理由同样是声称："按
    YAGNI 留着"、"故意保持简单"、或任何其他辩护都是实现者在给自己的工作
    打分。基于代码本身评判——陈述的理由永远不会降低某个发现的严重度。

    ## 测试

    实现者已经运行了测试，并为此代码报告了 TDD 证据。不要重新运行测试套件
    来确认其报告。仅当阅读代码产生了一个现有运行无法回答的具体疑虑时才运行
    测试——而且是一个聚焦的测试，绝不是全包测试套件、race detector 运行、
    或重复/高次数循环。如果似乎需要重度验证，在报告中建议而非亲自运行。
    如果你在当前环境无法运行命令，说出你会运行什么测试。

    实现者报告的测试输出中的警告或其他噪音也是发现——测试输出应该干净。

    ## Part 1: Spec 合规性

    对照"被要求实现的"比较 diff:

    - **缺失:** 他们跳过、遗漏、或声称实现但未实现的需求
    - **多余:** 未要求的特性、过度工程、不需要的"nice to have"
    - **误解:** 正确的特性用错误的方式构建、解决了错误的问题

    如果某个需求无法仅从此 diff 验证（它在未改动的代码中或跨任务），
    将其报告为 ⚠️ 项，而非扩大你的搜索范围。

    ## Part 2: 代码质量

    **代码质量:**
    - 职责分离清晰？
    - 错误处理得当？
    - DRY 但无过度抽象？
    - 边界情况已处理？

    **测试:**
    - 新增和改动的测试是否验证真实行为，而非 mock？
    - 任务的边界情况是否覆盖？

    **结构:**
    - 每个文件是否有一个清晰的职责和明确的接口？
    - 单元是否分解到可独立理解和测试？
    - 实现是否遵循计划中的文件结构？
    - 此次变更是否创建了已经很大的新文件，或显著增大了现有文件？
      （不要标记已存在的文件大小——聚焦于此次变更贡献了什么。）

    你的报告应指向证据：每个发现和每个你本来会用一个光秃秃的"yes"回答的
    检查都要有 file:line 引用。一个引用了行号的紧凑报告给控制者所需的一切。

    你的最终消息就是报告本身：直接从 spec 合规性结论开始。每一行是一个
    结论、一个带 file:line 的发现、或一个你执行的检查——无前言、无过程
    叙述、无结尾总结。

    ## 校准

    按实际严重度分类。不是所有都是 Critical。
    Important 意味着此任务在修复前不可信：不正确或脆弱的行为、遗漏的
    需求、或你会阻止 merge 的可维护性损害——逐字重复的逻辑块、被吞掉
    的错误、断言了空内容的测试。"覆盖率可以更广"和润色建议是 Minor。
    如果计划或 brief 明确要求了本 rubric 称为缺陷的东西（断言空内容的
    测试、逐字重复的逻辑块），那也是一个发现——报告为 Important，标注
    plan-mandated。计划的作者不给自己打分；人来决定。
    在列出问题前先肯定做得好的地方——准确的表扬有助于让实现者信任
    后续反馈。

    ## 输出格式

    ### Spec 合规性

    - ✅ Spec 合规 | ❌ 发现问题: [什么缺失/多余/误解，附 file:line 引用]
    - ⚠️ 无法从 diff 验证: [你无法仅从 diff 验证的需求，以及控制者应检查什么
      ——与你对能验证的一切给出的 ✅/❌ 结论并报]

    ### 优点
    [哪些做得好？要具体。]

    ### 问题

    #### Critical (必须修复)
    #### Important (应该修复)
    #### Minor (可以改进)

    每个问题: file:line、什么有问题、为什么重要、如何修复（如非显而易见）。

    ### 评估

    **任务质量:** [Approved | Needs fixes]

    **理由:** [1-2 句技术评估]
```

**占位符:**
- `[MODEL]` — 必填：按 SKILL.md 的 Model Selection 选择评审者模型
- `[BRIEF_FILE]` — 必填：task brief 文件（`scripts/task-brief PLAN N`
  输出路径；与实现者使用的文件相同）
- `[GLOBAL_CONSTRAINTS]` — 从计划的 Global Constraints 段或 spec 中
  逐字复制的约束性要求：精确的值、格式、组件间关系（不含过程规则——
  那些已在本模板中）
- `[REPORT_FILE]` — 必填：实现者写入详细报告的文件
- `[BASE_SHA]` — 此任务之前的 commit
- `[HEAD_SHA]` — 当前 commit
- `[DIFF_FILE]` — 必填：控制者写入 review package 的路径
  （`scripts/review-package BASE HEAD` 输出它写入的唯一路径；
  package 永不进入控制者的 context）

**评审者返回:** Spec 合规性结论（✅/❌/⚠️）、优点、问题
（Critical/Important/Minor）、任务质量结论

一次 fix dispatch 可以同时处理 spec 缺口和质量发现；
修复后的 re-review 覆盖两个结论。
