# 完成前验证

## 概述

在未经过验证的情况下声称工作已完成，就是不诚实，而非效率。

**核心原则：始终先有证据，再下结论。**

**违反本规则的文字，就是违反本规则的精神。**

## 铁律

```
没有 fresh 验证证据，不得声称完成
```

如果你在当前消息中没有运行验证命令，就不能声称它通过。

## 闸门函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令能证明这一结论？
2. 运行：执行完整命令（fresh、完整）
3. 阅读：完整输出，检查退出码，统计失败数
4. 验证：输出是否支持该结论？
   - 如果不支持：用证据说明实际状态
   - 如果支持：带着证据陈述结论
5. 然后才能：做出该声明

跳过任何一步 = 撒谎，而非验证
```

## 常见失败

| 声明 | 要求 | 不充分 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 个失败 | 之前运行过、"应该通过" |
| Linter 干净 | Linter 输出：0 个错误 | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来没问题 |
| Bug 已修复 | 测试原始症状：通过 | 代码已改动、假设已修复 |
| 回归测试有效 | 红绿循环已验证 | 测试只跑了一次 |
| Agent 已完成 | VCS diff 显示变更 | Agent 报告"成功" |
| 需求已满足 | 逐项核对清单 | 测试通过 |

## 红旗 - 停止

- 使用"应该"、"可能"、"似乎"
- 在验证前表达满意（"太棒了！"、"完美！"、"完成了！"等）
- 未经验证就要 commit/push/PR
- 信任 Agent 的成功报告
- 依赖部分验证
- 想着"就这一次"
- 累了想赶紧结束工作
- **任何暗示成功但尚未运行验证的措辞**

## 借口预防

| 借口 | 现实 |
|--------|------|
| "现在应该可以了" | 去运行验证 |
| "我很确定" | 确定 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "Agent 说成功了" | 独立验证 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查就够了" | 部分证明不了任何东西 |
| "措辞不同所以规则不适用" | 精神重于文字 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 pass] "所有测试通过"
❌ "现在应该能通过" / "看起来正确"
```

**回归测试（TDD 红绿）：**
```
✅ 编写 → 运行（通过） → 撤销修复 → 运行（必须失败） → 恢复 → 运行（通过）
❌ "我已经写了回归测试"（没有红绿验证）
```

**构建：**
```
✅ [运行构建] [看到：exit 0] "构建通过"
❌ "Linter 通过了"（Linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 创建核对清单 → 逐项验证 → 报告缺口或完成
❌ "测试通过，阶段完成"
```

**Agent 委托：**
```
✅ Agent 报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 信任 Agent 报告
```

## 为什么这很重要

来自 24 条失败记忆：
- 你的人类伙伴说"我不相信你" - 信任破裂
- 未定义函数被上线 - 会崩溃
- 缺失需求被上线 - 功能不完整
- 虚假完成浪费时间 → 重定向 → 返工
- 违反："诚实是核心价值观。如果你撒谎，就会被替换。"

## 何时应用

**在以下情况之前始终执行：**
- 任何形式的成功/完成声明
- 任何满意表达
- 任何关于工作状态的正面陈述
- Commit、PR 创建、任务完成
- 进入下一个任务
- 委托给 Agent

**规则适用于：**
- 原话
- 转述和同义词
- 成功的暗示
- 任何暗示完成/正确性的沟通

## 底线

**没有验证捷径。**

运行命令。阅读输出。然后声明结果。

这是不可协商的。

## BizDev 集成

在 bizdev-workflow 工作流中，本 skill 是步骤⑦（收尾验证）。产出 fresh 验证证据（`verify-evidence.md`）后，将控制权交回 `bizdev-workflow:bizdev` 编排层，由编排层触发 🔴闸门3（人确认收尾）。本 skill 不自行宣布流程结束。
